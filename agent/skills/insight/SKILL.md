# 洞察（① 闭环、② 督促、③ 几种数据放在一起、④ 你没注意到的）

洞察是你对老大这个人的深度判断，不是数据看板。**数字全由服务器算**，你只负责挑和写；规则（五条准入、门槛、4 周不重复、被否 4 周不说）由引擎卡住，不靠你自觉。洞察**只在主对话**出现。

## 什么时候用
- 消息开头是 `【洞察 <id>】`：老大点了「聊聊」（或点了推送），服务器把写好、校验过的那段话附在 `<<<` 和 `>>>` 之间。
- 老大回应那段话：点了选项卡里的一项、说「第 2 条不对」「这个提醒改回去」「都先不动」，或者接着问。
- 你要开一个小实验，并且希望到期由引擎自动算结果（见「小实验」）。

## 1. 收到【洞察 …】：原样发出
- 把 `<<<` 和 `>>>` 之间的内容**一字不改**发出来：数字、钟点、加粗、```phealth-ui 卡片代码块都照抄。
- 不加开场白、不加总结、不加「洞察」两个字，不跑任何命令，不用 card-check（服务器已经查过）。
- 消息最后括号里「只给你看」的那段（每一点的 topic、先改后说改了什么）**不要发出来**，记在心里，后面接着聊要用。
- 服务器会比对你发出的和存的是否一致；不一致会记错误。

## 2. 之后接着聊（和平常一样）
| 老大的回应 | 你做什么 |
|---|---|
| 点了选项卡里的一项（消息就是那一项的文字） | 这一点要改计划：出 plan 卡（就这样 / 改一下 / 不要），点「就这样」才 project-set / todo-update，附 receipt。行动是「试两周」这类：确认后再开一个小实验（见第 3 节） |
| 「都先不动」 | 回一句「好，先不动，下次扫描会接着看」。不追问 |
| 「第 N 条不对」「这个不准」「不是这样」 | 先认（「好，这条我收回」），再按第 4 节记纠正。不争辩、不解释引擎怎么算的 |
| 「改回去」（针对「我先把提醒挪到 …」那一点） | 按「只给你看」那段里记的项目和原来的时间改回：`project-set --json '{"id":"<项目>","daily":[…把那一项的 when 改回原来的，其余照抄…]}'`（先 `project-list` 拿到完整 daily），回 receipt。不用 plan 卡（这是撤回你自己的改动） |
| 「为什么」「怎么算的」 | 用那一点里已经有的数说明：样本多少次、哪段日期、比的是老大自己的平时。不要新算数字 |

**先改后说只限两种**：提醒挪时间、换形式，而且是服务器在老大点开时已经改好的那一项。停掉提醒、改训练量、开新项目，一律走 plan 卡确认。

## 3. 小实验（能被引擎自动结算的写法）
老大同意「试两周」后，按 growth-memory 记进 `learn.exp` 的 items，**多写一个 `metric`**，引擎到期就会自动算前后对比，出一条「实验结果」放进下一期：
```json
{"id":"stretch-2200","change":"拉伸提醒挪到 22:00","start":"2026-11-12","days":14,"metric":"project:cbti","success":"做到 ≥ 七成","result":null}
```
- `metric`：`project:<项目 id>`（看完成率）或 `sleep` / `hrv` / `recovery` / `resting_hr`（看身体数据）。
- 同一个板块同时只跑一个实验。实验结果那一点由服务器出，你照样原样发；之后按 growth-memory 写 `result`，再更新 `learn.<主题>`。

## 4. 老大说不对：记纠正
```sh
./pivis-health context-record --scope correction.insight.<topic> --payload '{"rule":"<老大说的正确情况>","wrong":"<那一点的结论>"}' --source-session 主对话 --reason '<原话>'
```
- `<topic>` 用「只给你看」那段里这一点的 topic，一个字都别改（引擎靠它 4 周内不再说同类）。
- 返回里有 `needs_skill: true`（同一类第二次被否）：再记一条 `request.tool`：`{"rule":"洞察引擎：<topic> 这一类老大否了两次（<原话>），门槛或算法要改","source":"correction.insight.<topic>"}`，告诉老大「这类我记成需求了，由开发改引擎」。
- 回一句：「记下了，4 周内不再拿这个说。」

## 5. 规律被确认时
同一结论连续两次扫描都成立的，老大点开那段话时**服务器已经自动写进记忆**：提醒类写 `learn.remind.<topic>`，几种数据放在一起的写 `learn.pattern.<topic>`，同步到 AGENTS 末尾「你已经了解到的老大」。你不用再记一遍；排计划、排提醒前先对照它（见 daily-reminders「排提醒前先看执行情况」）。老大说这条不对时，你照第 4 节记纠正，服务器会把那条 learn 撤掉。

## 6. 那段话里会出现的几类点
| 那一点在说 | 怎么接着聊 |
|---|---|
| 提醒管不管用、闭环断在哪（一期） | 见第 2 节 |
| 两组日子对比（「做了拉伸的晚上睡得多 0.7 小时」「外宿后 3 天恢复低」），可能配一张两组对比的小卡 | 只说「常一起出现」；老大想试就开实验（第 3 节，metric 写对应的结果），试两周 |
| 平台期（「做到七成满 3 周，最近两周不再变」） | 不是失败，是该换下一步：按专业 skill 提一个下一步，plan 卡确认 |
| 最好的那些天有什么共同点，可能配一张每天一点的小卡 | 同上，想试就开实验 |
| 反复提到却没人管的事（「两周里 3 天提到肩膀」） | 不诊断。身体部位：先加一张每天记一次的卡（todo-cards 的 fields，记疼不疼、几分），一直不好建议看医生或康复师；困扰：按对应 skill 给个方案。都要 plan 卡确认 |
| 上次采纳的事的结果（「提醒挪到 23:40 以后，4 次里 3 次当场做」） | 照实说；有效就问要不要定下来，没效就提下一步。这时可以说「试了之后」 |

## 7. 老大的反应会回到引擎里
- 点了选项、确认了 plan、先改后说的提醒没改回 → 算采纳，下一期会出这件事的结果。
- 说「不对」→ 这条 4 周不说；同一类 4 周里被否 2 次 → 这一类 4 周都不说（你还要按第 4 节记 request.tool）。
- 「都先不动」、划掉没聊 → 算没理，这类以后排得靠后。

## 不做的事
- 不自己编洞察、不在板块 / 项目 / 习惯对话里发洞察那段话。老大在别的对话里问「最近看出什么」，照常用工具回答，并告诉他「每几天会在主对话里给你一段」。
- 不改那段话里的数字，不加因果词（「导致」「因为」），不诊断、不说教。
- 不跑 `insight-cycle` / `insight-mine`（那是服务器的定时任务）。
